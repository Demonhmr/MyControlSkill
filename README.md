# Компас руководителя (MyControlSkill)

Приложение-концепт для руководителей: диагностика управленческой компетенции через 360°-обратную связь и рекомендации по развитию, построенные на модели из статьи Habr [«Почему руководители плохо руководят»](https://habr.com/ru/companies/smartvalues/articles/1064854/) (SmartValues, источник — исследования Френча-Рейвена и Zenger Folkman).

## Ключевая идея модели

1. **Деструкторы важнее всего.** Компетенция ниже 10-го перцентиля обнуляет эффект всех сильных сторон — их гасим первыми.
2. **Развитие среднего — пустая трата ресурса.** Диапазон 10–70 перцентиля почти не меняет восприятие лидерства. Продукт сознательно не предлагает подтягивать слабые стороны.
3. **Точка роста — на пересечении** силы (≥70 перцентиль), личного интереса и потребности команды/организации.
4. **Развитие через компетенции-спутники и «трудные диалоги»**, а не через универсальные тренинги — только так сильная сторона (70–90 перцентиль) переходит в статус «суперсила» (90+).

## Структура репозитория

```
MyControlSkill/
├── docs/                     — разбор статьи, концепция, методология (см. ниже)
├── prototype-html/           — кликабельный прототип на чистом HTML/CSS/JS (без сборки)
├── pitch-deck/               — презентация для инвесторов (HTML-слайды)
├── app/                      — рабочее React-приложение (Vite)
├── cmd/launcher/             — .exe с вшитым прототипом (демо без бэкенда)
├── cmd/server/               — сетевой сервер (SQLite)
├── internal/                 — общий Go-код: отдача SPA, конфиг, хранилище, скоринг
├── deploy/                   — юниты systemd, конфигурации прокси, копии базы
└── scripts/build.sh          — сборка бинарников
```

Go-код собран в один модуль `mycontrolskill`: лаунчер и сервер отдают
одностраничное приложение общим обработчиком `internal/web`.

### `prototype-html/`

Один файл `index.html`, открывается двойным кликом в браузере — без сборки, без зависимостей. Быстрый способ показать сценарий кому-то без установки Node.js.

### `pitch-deck/`

Один файл `index.html` — 13-слайдовая презентация для инвесторов: проблема, диагноз, слепая зона рынка, концепция «Деструктор → Суперсила → Спутники», продукт, статус реализации, сегменты рынка, форма монетизации, защищаемость и дорожная карта по фазам (без цен и дат — по просьбе). Открывается в браузере, навигация стрелками/кликом/точками внизу, печатается в PDF через Ctrl+P (каждый слайд — отдельная страница).

### `cmd/launcher/` — демо-режим

Сборка прототипа в самодостаточный `.exe` для Windows. Статика Vite вшивается
в бинарник (`go:embed`), при запуске поднимается локальный сервер на свободном
порту и открывается браузер. У пользователя не нужен ни Node.js, ни установка —
один файл на 6 МБ. Бэкенда нет: данные лежат в localStorage браузера.

```bash
./scripts/build.sh            # лаунчер и сервер
./scripts/build.sh launcher   # только лаунчер
```

Требуется Go (ставится распаковкой архива с go.dev/dl, без sudo). Собранные
бинарники в репозиторий не коммитятся.

Почему сервер, а не открытие `index.html` напрямую: сборка Vite использует
ES-модули, а браузеры блокируют их загрузку с `file://` из-за CORS.

Каталог `cmd/launcher/dist/` содержит только `.gitkeep`: сама статика
собирается скриптом, но каталог обязан существовать, иначе `go:embed`
не компилируется на чистом клоне.

### `cmd/server/` — сетевой режим

Сервер для реального сбора 360°: респонденты заполняют анкеты по своим
ссылкам со своих устройств. Данные в SQLite, драйвер `modernc.org/sqlite`
(чистый Go — сборка остаётся статической, `CGO_ENABLED=0`).

```bash
./scripts/build.sh server     # → build/mycontrolskill-server
go run ./cmd/server
```

Настройки через переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MCS_ADDR` | `:8080` | адрес прослушивания |
| `MCS_DB_PATH` | `data/mycontrolskill.db` | файл SQLite (каталог создаётся сам) |
| `MCS_STATIC_DIR` | `app/dist` | сборка фронтенда, отдаётся с диска |
| `MCS_BASE_URL` | — | внешний адрес; нужен для ссылок-приглашений |
| `MCS_TRUST_PROXY` | — | брать адрес клиента из `X-Forwarded-For` |

Миграции применяются при старте (`internal/store/migrations`), повторный
запуск безопасен. `GET /healthz` отвечает 200 только если база доступна.

#### Вход

Пароля нет: руководитель вводит почту, получает одноразовую ссылку и по ней
входит. Ссылка живёт 15 минут, сессия — 30 дней; в базе лежат только хэши
токенов, поэтому из дампа рабочие ссылки не восстановить.

```
POST /api/auth/login      {"email":"..."} → 202, ссылка уходит письмом
GET  /api/auth/callback   ?token=...      → 303 на /, ставит cookie сессии
GET  /api/me                              → 200 или 401
POST /api/auth/logout                     → 204
```

Cookie сессии — `HttpOnly` (её не украдёт XSS), `SameSite=Lax` (при `Strict`
переход из почтового клиента не донёс бы её до приложения), `Secure`
включается автоматически, когда `MCS_BASE_URL` начинается с `https://`.

#### Почта

Настраивается переменными окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MCS_SMTP_HOST` | — | адрес сервера; пуст — письма не отправляются |
| `MCS_SMTP_PORT` | `587` | порт |
| `MCS_SMTP_SECURITY` | `starttls` | `starttls`, `tls` (порт 465) или `none` |
| `MCS_SMTP_USER` | — | логин; по нешифрованному каналу не отправляется |
| `MCS_SMTP_PASSWORD` | — | пароль |
| `MCS_SMTP_FROM` | — | отправитель, можно `Имя <box@example.com>` |

Без `MCS_SMTP_HOST` сервис работает, но ссылки только пишутся в лог со
`WARN` — войти сможет лишь тот, у кого есть доступ к логам. Для разработки
это удобно, для боевого запуска нет, поэтому предупреждение громкое.

Если почта настроена, при старте проверяется и `MCS_SMTP_FROM`, и
`MCS_BASE_URL`: без первого письма отвергнет первый же приличный сервер, без
второго ссылку в письме не из чего собрать. Узнать об этом лучше при старте,
чем при первой попытке входа.

Тело письма кодируется в base64 целиком. Дело не в экономии: тексты русские,
в quoted-printable они превращаются в кашу из `=D0=9F`, а строки SMTP
ограничены 998 байтами — абзац кириллицы переваливает за предел незаметно.
Тема кодируется по RFC 2047, иначе доедет как «????».

#### Ограничение частоты

Отправка писем — это возможность рассылать их по чужим адресам, поэтому
запрос ссылок ограничен с двух сторон:

| Что ограничено | Предел | Серия подряд |
|---|---|---|
| ссылки на один адрес почты | 5 за 15 минут | 2 |
| ссылки с одного источника | 20 за час | 5 |
| приглашения от одного руководителя | 60 за час | 10 |

Ограничений именно два, и одного не хватило бы: предел по адресу не даёт
завалить письмами один ящик, но обходится сменой адреса в каждом запросе —
от этого защищает предел по источнику. Приглашения ограничены отдельно:
аккаунт заводится первой же ссылкой, так что вход чужой рассылке почти не
мешает.

Отказ — `429` с заголовком `Retry-After`. Некорректный адрес почты лимит не
тратит: опечатка не должна лишать человека права на попытку.

Счётчики живут в памяти процесса. Для одного экземпляра этого достаточно;
при нескольких экземплярах предел окажется у каждого свой.

**`MCS_TRUST_PROXY=true`** нужен, когда перед сервисом стоит обратный
прокси: иначе все запросы выглядят пришедшими с его адреса, и предел по
источнику либо бессмыслен, либо блокирует всех разом. Берётся последнее
значение `X-Forwarded-For` — его дописал ближайший прокси, то есть наш; всё,
что левее, мог прислать сам клиент. Без прокси переключатель включать нельзя:
заголовок тогда подделывается и ограничение обходится.

Остаётся один известный пробел: первый переход по ссылке создаёт аккаунт, то
есть завести его может любой, кто знает адрес сервиса. Закрывается перед
публичным запуском, для закрытого пилота приемлемо.

#### Раунды и приглашения

```
POST /api/assessments                  {"title":"..."} → 201
GET  /api/assessments                                  → список со счётчиками
GET  /api/assessments/{id}                             → раунд + приглашения
POST /api/assessments/{id}/close                       → закрыть раунд
POST /api/assessments/{id}/invites     {"role","email"} → 201, ссылка в ответе
GET  /api/assessments/{id}/profile                     → 200 или 423
```

Ссылка на анкету возвращается ровно один раз, при создании приглашения: в
базе лежит только хэш токена, показать её повторно нельзя — можно лишь
выдать новую.

Профиль ниже порога в три внешние анкеты отдаёт **423 Locked** со
счётчиками, но без единого перцентиля. Счётчики в теле отказа — чтобы
интерфейс показал «собрано 2 из 3» без второго запроса.

Чужой раунд отвечает 404, а не 403: по разнице между этими ответами
перебором идентификаторов выяснялось бы, какие раунды существуют у других.

#### Рабочее состояние руководителя

```
GET  /api/state        → отметки экранов + записи тренажёра одним ответом
PUT  /api/state        → перезапись целиком, 204
POST /api/reflections  → 201, запись из тренажёра
```

Состояние перезаписывается целиком, а не по полям: это набор отметок одного
экрана, редактирует их один человек со своего устройства, и слияние
изменений тут ничего не решает.

Запись сохраняется **отложенно** (800 мс): отметка интереса меняет состояние
на каждый клик. И **только после загрузки** — пока состояние с сервера не
прочитано, писать нельзя, иначе значения по умолчанию затрут то, что там
лежит. Если чтение не удалось, запись не включается вовсе и приложение
показывает, что изменения не сохраняются.

Запись из тренажёра сначала уходит на сервер и только потом появляется на
экране: иначе при сбое она осталась бы в окне и нигде больше, а руководитель
считал бы практику зафиксированной.

`responses` на сервер не уходят — в сетевом режиме анкеты живут в своих
таблицах, а этот массив принадлежит демо-режиму.

#### Анкета респондента

```
GET  /api/survey/{token}   → контекст: роль, кого оценивают, погашена ли ссылка
POST /api/survey/{token}   → 201, ссылка гаснет
```

Без авторизации: аккаунта у респондента нет и не будет, вся его
аутентификация — знание токена из ссылки. Роль приходит из приглашения, а не
из тела запроса: её назначает руководитель, и подмена на `self` исключила бы
анкету из расчёта.

Использованная ссылка и закрытый раунд отдают на `GET` не ошибку, а 200 с
пометками `used`/`closed` — респонденту нужно объяснение на экране, а не
пустая страница.

Текстов вопросов сервер не хранит и не отдаёт: анкету рисует клиент из
`app/src/data/questionnaire.js`. Сервер проверяет коды, а не формулировки,
поэтому дублировать девятнадцать компетенций с текстами незачем.

#### Два режима одной сборки

Приложение работает и без бэкенда, и с ним, одной и той же сборкой:

- **local** — так работает `.exe`: данные в localStorage, входа нет,
  раунды недоступны (приглашать некого);
- **server** — за приложением стоит бэкенд, без входа приложение ничего не
  покажет, в навигации появляется экран «Раунды 360°».

Режим определяется в рантайме пробой `/api/me`, а не флагом сборки: флаг
означал бы две разные сборки и, рано или поздно, перепутанные артефакты.
Различает режимы **тип содержимого, а не код ответа** — лаунчер на любой
неизвестный путь отдаёт оболочку приложения с кодом 200, поэтому по статусу
он от сервера неотличим, а `text/html` вместо `application/json` отличим
однозначно.

Профиль в этих режимах берётся из разных мест (`app/src/state/profile.jsx`).
В local он считается на клиенте из анкет в localStorage и ниже порога
респондентов подставляет демонстрационные значения — это витрина прототипа,
так и задумано. В server профиль приходит с сервера уже посчитанным, а
**демонстрационных значений нет вовсе**: пока анкет меньше трёх, экраны с
числами не показываются, вместо них — состояние сбора со счётчиками. У
демо-значений та же форма, что у настоящих, и руководитель принял бы витрину
прототипа за результат замера своей команды.

Экран «Опрос 360°» в сетевом режиме скрыт: анкеты заполняют приглашённые по
своим ссылкам, а он пишет в localStorage и ни на что не влияет.

Экран респондента — отдельный вход в приложение по пути `/s/:token`
(`app/src/screens/RespondentSurveyScreen.jsx`): без навигации, без стора и
без доступа к профилю руководителя. Разбор пути живёт в `main.jsx` до
создания стора; полноценный роутер ради одного маршрута не заводился.

**Известное ограничение анонимности.** Руководитель видит, кто из
приглашённых уже ответил (`usedAt`) — это нужно, чтобы напоминать
неответившим, и так устроены все инструменты 360°. Но вместе с обновлением
профиля после каждой анкеты это даёт теоретическую возможность вычислить
отдельного респондента, сравнивая профили до и после. Порог в три анкеты
такую атаку затрудняет, но не закрывает; полноценная защита — отдавать
профиль только после закрытия раунда.

```bash
go test ./...    # тесты Go
```

### `app/`

Полноценное React-приложение (Vite), реализующее ту же логику: реальная форма 360° вместо моков, персистентность в localStorage, тесты на ключевую бизнес-логику (Vitest + React Testing Library).

**Запуск:**
```bash
cd app
npm install
npm run dev      # приложение на http://localhost:5173
npm test         # тесты в watch-режиме
npm run test:run # один прогон (для CI и скриптов)
npm run build    # прод-сборка
```

Демо-сценарий: экран «Опрос 360°» → «Деструкторы» (видна критическая зона «нет видения») → отметить как проработанную (или заполнить ≥3 анкеты 360° для реального расчёта) → «Карта силы» → «Точка роста» → «План развития» → «Тренажёр» → «Пульс-трекер» → «HR-дашборд».

## Статус проекта

Прототип для проверки концепции (не production). Данные по умолчанию — демонстрационные (seed-значения), заменяются реальными после сбора ≥3 внешних ответов 360° на каждого оцениваемого.

## Развёртывание

Сервис — один статический бинарник и файл SQLite рядом: ни отдельной СУБД,
ни рантайма на сервере не нужно. Юниты systemd, конфигурации Caddy и nginx,
ежедневные копии базы и порядок восстановления — в [`deploy/`](deploy/).

Копия базы делается самим бинарником (`mycontrolskill-server -backup ФАЙЛ`),
а не копированием файла: при включённом WAL свежие изменения лежат в
отдельном журнале рядом, и копия одного лишь `.db` теряет почти всё.

## Дальнейшие шаги

Backend — в работе. Готово: каркас сервера, SQLite с миграциями, общая
отдача SPA, схема и слой доступа к данным (`internal/store`), словарь
методики (`internal/domain`), скоринг на сервере (`internal/scoring`),
вход по одноразовым ссылкам и сессии (`internal/api`).

Анонимность заложена в схему: у `response` нет ссылки на `invite`, поэтому
оценки нельзя сопоставить с почтой респондента даже по дампу базы.
Одноразовость ссылки обеспечивается погашением приглашения в той же
транзакции, что и запись анкеты.

### Две реализации скоринга

`app/src/logic/scoring.js` остаётся ради демо-режима без бэкенда,
`internal/scoring` считает то же самое на сервере. Расчёт переехал не ради
скорости: чтобы посчитать профиль на клиенте, пришлось бы отдать ему сырые
ответы, а по ним руководитель восстановил бы, кто именно как отвечал.

Разъезжаться реализациям нельзя — иначе один и тот же руководитель увидит
разные перцентили в `.exe` и в вебе. За этим следит сверка по эталонным
векторам, снятым с клиентской версии:

```bash
./scripts/gen-golden.sh   # → internal/scoring/testdata/golden.json
go test ./internal/scoring/
```

Если Go-тест упал, сначала разбираемся, какая из реализаций неправа, и
только потом перегенерируем эталон.

Одно отличие сделано намеренно: ниже порога в 3 внешние анкеты клиент
подставляет демонстрационные значения из `data/index.js`, а сервер не
отдаёт перцентиль вовсе. Выдавать витрину прототипа за результат замера
нельзя.

Осталось:
